# design-check フィクスチャの理論値

`tests/make_fixtures.py` が生成する合成画像は、すべて **同じ幾何パラメータから理論値を計算できる**
ように設計している。値を変える場合は `make_fixtures.py` と本ファイルを必ず一緒に更新すること。

生成:

```bash
uv run tests/make_fixtures.py --out-dir <出力先>
```

座標系はすべて `[x0, y0, x1, y1]`（x1, y1 は半開区間の上限。PIL の crop / numpy slicing と同じ）。
ピクセル重心は「ピクセル中心（index + 0.5）」で計算するため、一様な矩形の重心は
その bbox の算術中心 `(x0+x1)/2, (y0+y1)/2` と厳密に一致する（設計上の前提）。

## ① 重心フィクスチャ: `gravity_rect.png`（340×240px）

R1・R2 の2つの黒矩形（背景は白）を組み合わせ、全体のインク重心が
タイトな bbox の幾何中心からズレるように設計している。

- R1: ローカル座標 `x:[0,39) y:[100,200)` → 面積 `A1 = 39*100 = 3900`、中心 `(19.5, 150)`
- R2: ローカル座標 `x:[250,300) y:[0,95)` → 面積 `A2 = 50*95 = 4750`、中心 `(275, 47.5)`
- 全体を `(+20, +20)` 平行移動して 340×240 キャンバスの中央付近に配置（並進不変なので Δ には影響しない）

理論値（分数は `fractions.Fraction` で厳密計算、小数は概算）:

| 項目 | 値 |
|---|---|
| タイト bbox（並進後） | `[20, 20, 320, 220]` |
| 幾何中心 | `(170, 120)` |
| インク重心 | `(27646/173, 32425/346) ≈ (159.8035, 93.7139)` → 並進後 `(179.8035, 113.7139)` |
| Δx | `1696/173 ≈ 9.803468 px` |
| Δy | `-2175/346 ≈ -6.286127 px` |
| Δ magnitude | `≈ 11.645745 px` |
| 要素幅 | `300px` → Δ% ≈ `3.83%` → **flag: red**（閾値: green<0.5% / yellow<1.5%） |

`rois.json` の ROI 座標は目視ラフ入力を想定した緩い bbox `[10, 10, 330, 230]` を与える
（`refine_bbox` が pad=2 込みで `[18, 18, 322, 222]` にタイト化するが、pad は対称なので
幾何中心の値には影響しない）。

**実測結果（analyze.py gravity）**: `Δx=9.803468208092482, Δy=-6.286127167630056`
→ 理論値との差は `< 1e-8px`（許容誤差 ±1px を大きく下回る）。

`gravity_shape` ROI には `"relative_to": "gravity_shape"`（自己参照）を持たせている。
これは「このシェイプが元々収まっていた枠」を固定参照点として、
`simulate.py offset` の補正効果を検証するために使う（後述）。

### simulate.py offset の検証

自動補正量 `dx,dy = -round(Δx), -round(Δy) = (-10, 6)` を適用して要素を平行移動し、
移動前に確定した固定参照点（上記幾何中心）に対して再計測する。

理論上の残差 = `(Δx - 10, Δy + 6) = (-0.196532, -0.286127)` → magnitude `≈ 0.347 px`

**実測結果（simulate.py offset --dx/--dy 自動）**: `after_delta_px = 0.34712173842382443`
→ **< 1px を満たす**（受け入れ基準を達成）。

## ② カーニングフィクスチャ: `kerning_string.png`

6個の黒矩形グリフ（幅20px・高さ60px）を白背景に並べたダミー文字列。

ローカル座標（オフセット前、`x` は `[start, end)`）:

| glyph | x range | 直前ギャップ |
|---|---|---|
| 1 | `[0, 20)` | - |
| 2 | `[30, 50)` | 10px |
| 3 | `[60, 80)` | 10px |
| 4 | `[105, 125)` | **25px（異常値）** |
| 5 | `[135, 155)` | 10px |
| 6 | `[156, 176)` | **1px（濁点等を模した微小ギャップ→ glyph5 と結合される）** |

結合閾値は「結合前の生ブロブ間ギャップの中央値 × `merge_gap_ratio`（デフォルト0.15）」
（下限 `min_gap_px`、デフォルト1.0px）で決まる（下記「濁点結合バグの修正」を参照）。
この5ブロブの生ギャップは `[10, 10, 25, 10, 1]` → 中央値10px → 閾値 `max(1.0, 10*0.15)=1.5px`。
glyph6直前の1pxギャップ（`1 < 1.5`）だけが結合対象になり、glyph5+6 は幅41pxの
1ブロブ（`ink_pct` は他の約2倍）として検出される。

理論値:

| 項目 | 値 |
|---|---|
| 結合閾値 | `1.5px`（`max(1.0, 10*0.15)`） |
| 結合後ブロブ間ギャップ | `[10, 10, 25, 10]` |
| 中央値ギャップ | `10px`（4値の中央2値平均 = (10+10)/2） |
| 偏差(%) | `[0%, 0%, 150%, 0%]` |
| 最大偏差 | `150%` → **flag: red**（閾値: green<10% / yellow<25%） |

**実測結果（analyze.py kerning）**: `gaps_px=[10,10,25,10]`, `median_gap_px=10.0`,
`gap_deviation_pct=[0.0,0.0,150.0,0.0]`, `max_deviation_pct=150.0`, `flag=red`,
`merge_threshold_px=1.5` → **理論値と完全一致**。

### 濁点結合バグの修正と回帰フィクスチャ: `kerning_dakuten.png`

**バグ**: 当初の実装は結合閾値が固定の絶対px値（`min_gap_px=2`、`gap < min_gap_px` で結合）
だったため、高解像度画像（例: 4800px幅の名刺画像で通常ギャップが20〜30px）では
濁点相当の微小ギャップ（2px程度）が `2 < 2` を満たさず結合されなかった
（実データ `<名刺の実データ>/` のタグラインで再現: `gaps=[22,2,21,24,23,25,23,24,29,25,22]`,
`median=23` に対し `2 < 0.15*23=3.45` を満たすはずが結合されず12ブロブのまま検出されていた）。

**修正**: 結合閾値を「結合前の生ブロブ間ギャップの中央値 × `merge_gap_ratio`」という
解像度非依存の相対値に変更した（`analyze_kerning_bbox` の `merge_gap_ratio` 引数、デフォルト0.15）。

回帰フィクスチャ `kerning_dakuten.png`: 4文字を模した5ブロブ（c1, c2a, c2b, c3, c4）を配置し、
c2a-c2b間だけ3pxの微小ギャップ（濁点相当）、他は22pxの通常ギャップにしている。

ローカル座標（オフセット前）:

| ブロブ | x range | 直前ギャップ |
|---|---|---|
| c1 | `[0, 25)` | - |
| c2a | `[47, 67)` | 22px |
| c2b | `[70, 78)` | **3px（濁点相当→ c2a と結合される）** |
| c3 | `[100, 125)` | 22px |
| c4 | `[147, 172)` | 22px |

生ギャップ `[22, 3, 22, 22]` → 中央値22px → 結合閾値 `max(1.0, 22*0.15)=3.3px`。
`3 < 3.3` なので c2a+c2b が結合される。

理論値:

| 項目 | 値 |
|---|---|
| 結合閾値 | `3.3px`（`max(1.0, 22*0.15)`） |
| 結合後ブロブ数（文字数） | `4`（c1, c2(結合済み, 幅31px), c3, c4） |
| 結合後ブロブ間ギャップ | `[22, 22, 22]`（すべて均一） |
| 最大偏差 | `0%` → **flag: green** |

**実測結果（analyze.py kerning）**: `chars` が4件（2件目の `width_px=31`＝c2a(20)+gap(3)+c2b(8)）、
`gaps_px=[22,22,22]`, `max_deviation_pct=0.0`, `flag=green`, `merge_threshold_px=3.3`
→ **理論値と完全一致**（修正前の実装ではc2bが独立ブロブとなり5文字・
`gaps_px=[22,3,22,22]`・偏差86.4%・`flag=red` という誤検出になっていたことを確認済み）。

### 実データでの確認: `<名刺の実データ>/`（名刺タグライン、4800×2901px）

修正後、`tagline` ROI（濁点を含む日本語のタグライン）を実行した結果:

- `chars` 数: **11**（濁点結合済み。修正前は12）
- `gaps_px`: **`[22, 21, 24, 23, 25, 23, 24, 29, 25, 22]`**（修正前は `[22, 2, 21, 24, 23, 25, 23, 24, 29, 25, 22]` で
  独立した2pxギャップを含み11ギャップ・`median=23`・`max_deviation_pct=91.3%`・`flag=red` という誤検出だった）
- `merge_threshold_px`: `3.45`（`max(1.0, 23*0.15)`）
- 修正後: `median_gap_px=23.5`, `max_deviation_pct≈23.4%`, `flag=yellow`
  （実際のカーニングむら自体は残るが、濁点起因の偽陽性が解消された）

### 色コントラスト（黒/白）の検算

同フィクスチャの `text_line` ROI（黒グリフ + 白背景）を使い、
`analyze.py color --text-roi kerning_line` でコントラスト比を検算する。

理論値: 前景 `(0,0,0)`、背景 `(255,255,255)` → WCAG コントラスト比 `21.0:1`（最大値）

**実測結果**: `foreground_rgb=[0,0,0]`, `background_rgb=[255,255,255]`,
`contrast_ratio=21.0`, `wcag_normal_text=AAA` → **理論値と完全一致**。

## ③ サイズフィクスチャ: `size_squares.png`

側辺 `40 / 42 / 38 / 60` px の黒正方形4個（60が明確な外れ値）。

`visual_diameter = 2*sqrt(area/pi)`:

| id | side | area | visual_diameter |
|---|---|---|---|
| sq1 | 40 | 1600 | 45.135167 |
| sq2 | 42 | 1764 | 47.391925 |
| sq3 | 38 | 1444 | 42.878408 |
| sq4 | 60 | 3600 | 67.702750 |

- 平均 `mean ≈ 50.777063`
- 母標準偏差（`ddof=0`）`std ≈ 9.901487`
- `CV% = std/mean*100 ≈ 19.499921%` → **flag: red**（閾値: green<3% / yellow<8%）
- 外れ値: `sq4`（z-score ≈ 1.709 > 1.0）

**実測結果（analyze.py size）**: 上記の値と小数第4位まで完全一致（誤差 `< 1e-9`）。

## ④ 色フィクスチャ: `color_swatches.png`

ブランド6色（`common.py` の `BRAND_COLORS`）を各60×60pxで並べ、
その下段に「Lab空間で1軸だけ ±5.0 シフトして sRGB へ丸め直した色」を配置している
（丸め誤差でΔEはちょうど5.0にはならないため、実測ΔEを理論値として記載）。

⚠️ **下の表は同梱の中立パレットで測り直した値**（`common.py` の Lab / ΔE76 実装で算出）。
`BRAND_COLORS` を自分のブランド色に差し替えたら、**この表も測り直す必要がある**
（`make_fixtures.py` の `COLOR_SWATCHES` の `shifted_rgb` も同様）。

| ブランド | 元HEX | シフト後RGB | 実測ΔE76 | シフト軸 |
|---|---|---|---|---|
| Brand1 | `#3B82F6` | `(33,118,231)` | `4.929275` | L-5 |
| Brand2 | `#10B981` | `(39,185,120)` | `4.976083` | b+5 |
| Brand3 | `#F59E0B` | `(244,158,35)` | `5.020386` | b-5 |
| Brand4 | `#EC4899` | `(234,73,161)` | `4.626792` | b-5 |
| Brand5 | `#1E3A5F` | `(11,59,103)` | `4.977480` | b-5 |
| Brand6 | `#EDE4DA` | `(227,231,218)` | `4.980655` | a-5 |

許容誤差: 各ΔEは `5.0 ± 0.5` の範囲に収まる（Lab→sRGBの丸め・ガマット制約による）。
上の6件は `4.626792` 〜 `5.020386` で、この範囲に収まっている。

**実測結果（analyze.py color --n-colors 16）**: `consolidation_candidates` に上記6ペアが
すべて検出され、`delta_e` は表の値と小数第6位まで完全一致。
`brand_color_flags` では6色の元HEXが `delta_e=0.0, exact_match=true`、
シフト後の6色が `exact_match=false`（2.3 ≤ ΔE ≤ 10 の範囲内）として検出される
→ **理論値と完全一致**。

## PDF 変換の実機検証（Step 1）

`sips -s format pdf <png> --out test.pdf` → `sips -s format png test.pdf --out out.png` の
往復では、埋め込み画像の解像度がそのまま「1pt = 1px」で解釈されるため、
**名刺サイズ（252×144pt = 3.5×2in）の実ベクターPDFを直接 sips で PNG 化すると
`pixelWidth=252` にしかならない**（72dpi問題を実機で確認済み）。

対策として `qlmanage -t -s 4800 -o <出力先> <pdf>` にフォールバックすると、
同じベクターPDFから `pixelWidth=4800`（長辺≥1500pxの要件を余裕でクリア）の
PNGサムネイルが得られることを確認した。出力ファイル名は `<元ファイル名>.png`
（例: `card.pdf` → `card.pdf.png`）になる点に注意。

→ SKILL.md のワークフローでは「まず `sips` で変換し `sips -g pixelWidth` で
長辺を確認、1500px未満なら `qlmanage -t -s 4800` にフォールバックする」手順を採用する。
